# Jolt 5.6 feature coverage

This document is the authoritative feature inventory and qualification ledger for the standalone Jolt Gem. It describes the current
working tree; it is not a roadmap-completion claim. Native Jolt remains a private implementation detail built by `JoltNative.cmake`.

## Classification contract

Every Jolt 5.6 subsystem is assigned exactly one classification:

- **Publicly exposed**: an AZ-facing API exists without public `JPH` types.
- **Used privately**: native functionality implements an exposed feature but is intentionally hidden behind the Gem boundary.
- **Replaced by engine facility**: an engine service owns the corresponding responsibility.
- **Upstream limitation**: Jolt 5.6 cannot provide the capability without upstream work or a maintained native extension.
- **Deferred platform integration**: the design is intentionally excluded until a platform owner can qualify it.
- **Missing**: the native capability should be exposed, but the required Gem surface or proof is incomplete.

For a **Publicly exposed** row, `C++ and authoring proof` names current evidence and `Scenario and performance proof` names current or
required evidence. `Required` is an open qualification gate, not evidence. `N/A` means the subsystem has no meaningful component,
serialization, scenario, or benchmark surface; it never means that applicable proof was omitted.

## Qualification rules

- Keep this Markdown human-maintained. Do not add a companion schema or generate this file.
- The Phase-6 validation entry point will fail when a Windows row remains **Missing**, or when a **Publicly exposed** row has no named
  C++ proof and no explicit scenario/performance disposition.
- A passing aggregate target does not qualify a row. Applicable success, failure, stale-handle, mutation, concurrency, determinism,
  snapshot, serialization, editor, script, allocation, and performance axes must be named explicitly.
- Deterministic compilation, precise floating-point state, no contraction, worker scopes, canonical query/event ordering, callback-state
  fingerprints, and snapshot revision checks are mandatory shipping defaults.
- Optional simulation or diagnostic counters must pass in enabled and disabled builds. Disabled APIs return an explicit unavailable
  result; they never fabricate zero measurements.
- Release performance artifacts require at least 30 repetitions, matching workload signatures and policies, raw samples, median parity,
  bootstrap and tail bounds, and coefficient of variation at most 5%. Profile captures are diagnostic only.
- Assembly inspection is diagnostic and must report stack frames, out-of-line calls, branches, conversions, vectorization, copies, and
  inlining boundaries for selected hot functions. Do not gate exact opcodes.
- The WSL2 Clang checkpoint is diagnostic rather than native-Linux qualification. Repeat on native Linux hardware after Windows
  stabilizes. macOS follows `APPLE_QUALIFICATION.md`; iOS and other device platforms remain separately reported external gates.
