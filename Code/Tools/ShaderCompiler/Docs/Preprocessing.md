# Native AZSL preprocessing

AZSL preprocesses source tokens before the ANTLR parser. The normal compiler path does not create a flattened translation unit or write a preprocessing product. `azslc -E` is an explicit streaming export for investigation and interchange.

## Ownership and interfaces

This experiment on `no-mcpp-2` separates native preprocessing from the shared spelling storage saved on `no-mcpp-1` at `4a44460292`. Preprocessing tokens, macro names, macro parameters, classification-cache keys and resolved filenames own ordinary `std::string` values. Copying a token copies its spelling; generated spellings use the same representation. There is no spelling arena or persistent text-span representation.

`CompilationUnit` owns the source manager, final preprocessing tokens, dependency events and diagnostics. It accepts one `PreprocessRequest`; `PreprocessResult` exposes borrowed `AZStd::span<const T>` sequences after preprocessing completes. These spans describe result containers, not shared string storage. Keep the unit alive until parsing, semantic analysis, reflection, diagnostics and emission finish because source-location handles refer to its manager.

`SourceManager` caches file contents by canonical physical identity for consistent repeated includes and diagnostics. Buffers and include instances are ordinary vector values and may move as the containers grow. Each scanner gets an owned copy of its input, so opening a nested include cannot invalidate an outer scanner. Include spelling and resolution paths remain separate from file identity: relative includes use the include instance's resolution path, including aliases. Original UTF-8 bytes and physical line tables are retained for source locations; scanning removes line continuations from each token's copied spelling.

Source and expansion records remain because preprocessing needs file, macro and include provenance regardless of string ownership. A `SourceLocationId` identifies a record in the unit. A `SourceLocation` crossing a compiler API carries its manager and ID. Resolving an expansion normally returns the use site; spelling resolution returns its definition/argument origin. Include instances link to the include directive. `#line` changes presumed locations, not physical file identity. Resolved filenames are returned by value.

`PreprocessingTokenSource` adapts the completed sequence to `antlr4::CommonTokenStream`. `SourceToken` uses `CommonToken`'s ordinary owned text and adds only a source-location handle. ANTLR and compiler emission both use `getText()`. ANTLR character start/stop indices are unspecified (`INVALID_INDEX`); physical provenance is available through the source manager, and parser token indices still support AST intervals and code mutators. A parser interval crossing files or expansions cannot be interpreted as one source substring.

Fixed language spellings come from the generated vocabulary. The adapter recognizes vocabulary punctuation spanning multiple preprocessing tokens (for example `[[`). Other spellings are classified with the generated AZSL lexer over a normal `ANTLRInputStream`, bounded to one token. This temporarily decodes that token to UTF-32. Classification results are cached with owned string keys; there is no custom borrowed character stream and no second independent AZSL keyword/literal grammar. Short-lived views used for comparisons and expression scanning refer to owned strings or literals and are not stored in macro/source tables.

## Dialect

The preprocessing baseline is C++20, with AZSL-specific language and platform decisions described below. The implementation is compiler-owned; no external preprocessing library is built, linked, staged or executed. Clang is used as a development reference and optional test oracle. The engine's `-C -+` configuration remains accepted.

Preprocessing and AZSL syntax have separate contracts. Modern literal spellings and Unicode identifiers can participate in macros, stringification, inactive code and preprocessing expressions. Tokens reaching the parser must still be valid AZSL. This work does not add C++ types, user-defined literal semantics, language attributes, modules or header units to AZSL. `__has_cpp_attribute` validates its operand and returns zero because AZSL does not implement C++ language attributes. `__cplusplus` reports the preprocessing baseline, `202002L`; `__AZSL__` distinguishes this compiler from a C++ frontend.

Compiler-specific command-line extensions, `include_next`, GNU named variadics and GNU comma swallowing are outside this dialect. C++20 does not translate trigraphs, and no legacy C trigraph mode is provided. C++23 directives such as `#elifdef` are outside the selected baseline. Unsupported directives and command switches are errors. Unknown ordinary pragmas are retained for downstream shader compilation.

Supported constructs:

- Object, function and `...`/`__VA_ARGS__` macros; prescan, substitution, rescanning, `#` and `##`, empty arguments and placemarkers. Argument tokens next to `#`/`##` use unexpanded spellings. `__VA_OPT__` tests the expanded variadic argument and supports stringification, pasting and boundary placemarkers; invalid/nested uses diagnose at definition time. Empty replacements preserve whitespace needed by later stringification. Macro suppression uses the function invocation/closing-parenthesis intersection rule. Identical redefinitions are accepted; incompatible definitions, missing object-macro whitespace, reserved builtin changes and invalid variadic parameters diagnose an error.
- `#if`, `#ifdef`, `#ifndef`, `#elif`, `#else`, `#endif` and `defined`. C++ boolean constants and alternative operators are recognized; undefined identifiers become zero in expressions. Expressions use signed/unsigned 64-bit integers, conventional precedence and a conditional operator. Binary integers, digit separators, and standard integer suffix combinations are supported. Invalid suffixes and unrepresentable integers diagnose. Arithmetic uses explicit unsigned storage to avoid host signed-overflow undefined behavior; evaluated signed overflow diagnoses. Logical and conditional operands short-circuit; invalid syntax is still diagnosed in unevaluated operands. Division by zero and invalid shifts diagnose only in evaluated operands.
- Quoted and angled includes, macro-generated include names, guards, `#pragma once`, repeated includes under different definitions and ordered forced includes. Quoted includes search the including instance's directory first, followed by configured directories; angled includes search configured directories. Direct header names have their own lexical context: no internal macro expansion, comment recognition or escape interpretation. Macro-generated quoted names also retain backslashes. `__has_include` shares include resolution but does not open or preprocess the queried file. Query dependency events include an empty resolved path when the file is absent.
- `#undef`, `#error`, `#warning`, `#line` and retained non-`once` pragmas. `_Pragma` accepts ordinary, encoded and raw string operands using Clang's destringization behavior (C++20 wording only explicitly describes ordinary/wide operands). It validates its operand during argument prescan and defers execution until rescanning; discarded or stringified arguments do not execute it. `__FILE__` and `__LINE__` use presumed locations. An empty `#line` filename is distinct from an omitted filename; filename escapes are decoded and builtin/export strings are escaped when written. `__DATE__`, `__TIME__`, `__cplusplus`, `__STDC_HOSTED__` (zero) and `__AZSL__` are provided.
- Comments, ordinary/prefixed/raw strings, character literals, user-defined literal token boundaries, BOMs and LF/CRLF continuations. Raw-string bodies retain physical backslash/newline sequences. Digraphs, alternative operator spellings and the `<::` tokenization exception are supported. Unicode macro names use the C++20 identifier ranges in N4861 tables 2 and 3; UCN and UTF-8 spellings of a name identify the same macro. Comments remain available on ANTLR's comment channel. Original UTF-8 source bytes are retained.

Execution-character decisions are independent of the build host: UTF-8 source, signed 8-bit ordinary characters, 32-bit wide characters, and unsigned `u8`/`u`/`U` character values. Ordinary multi-character constants pack up to four bytes in source order; prefixed multi-character constants and characters that do not fit their literal encoding diagnose. These are documented implementation choices, not inferred properties of the host C++ compiler. C++ feature-test macros for unsupported AZSL language features are not advertised.

Inactive branches retain lexical and conditional structure, but do not expand ordinary macros, open includes, execute errors/warnings or undergo AZSL syntax checking. Nested `#ifdef`/`#ifndef` operands in skipped groups are ignored. Each invocation has a fresh macro/include context. Include depth defaults to 256, macro argument and conditional/expression nesting to 256, expansion count to 1,000,000, and buffered token count to 4,000,000. Physical source offsets and location IDs have checked 32-bit bounds. Limit failures identify the responsible source location.

Existing compiler diagnostic numbers retain their values. Native preprocessing adds error 600 and warning 601. Diagnostics resolve the use site and append expansion/include notes. Original declarations, reflection and emitted HLSL mappings use source handles instead of a global line finder. HLSL `#line` suppression checks filename as well as line progression.

## Command line

Native preprocessing is the default for every filename extension. `-I`, `-D` and `-U` accept attached and separate arguments. Include directories retain order; define/undefine operations execute in command order. A later command-line definition replaces an earlier one, preserving configuration-layer overrides. `--include file` is repeatable. `-C` preserves comments and `-+` selects the compatibility dialect; both are defaults. `-` reads stdin and resolves relative includes from the working directory.

`-E` streams preprocessed text to stdout or `-o`. It preserves token boundaries and emits location markers; it does not concatenate the translation unit in memory. `--preprocessed` reads historical preprocessed input, including input line markers immediately following language tokens. It bypasses includes and macro execution. The test harness explicitly identifies legacy fixtures; ordinary shader tests use native mode.

## Builder contract

The shader builder passes the original source, the resolved RHI header as a forced include, ordered include directories, and the merged global/platform/RHI/shader/supervariant arguments. Relative configured include and forced-include paths resolve against the project. Argument arrays stay arrays through process launch. `AzslCompiler::Compile` and `RHI::ExecuteShaderCompiler` each accept a single `AZStd::span<const AZStd::string>` interface; AZSL, DXC, DXSC, SPIRV-Cross and Metal callers build argument arrays directly. Each configured array entry is one argument, with no shell quoting around paths or values. Switch/value pairs must use separate entries (for example, `["--msl-version", "20300"]`); the bundled macOS and iOS settings follow this convention. On Windows, array serialization follows the Microsoft CRT quoting rules, including trailing backslashes and literal quotes.

Argument merging still deduplicates individual strings. To override a separate switch/value pair, remove both inherited entries before adding the replacement; macOS explicitly removes the global MSL 2.1 pair before adding MSL 2.3. This preserves the existing merge/removal rules without adding command-line parsing to process launch.

`CreateJobs` retains conservative dependency traversal, missing-file candidates and material-pipeline macro handling. It also traverses each effective configured include environment and forced header, and recognizes direct `__has_include` probes and digraph includes. Dependency discovery uses a forward-only byte scanner over borrowed source text, with no regex engine or flattened copy. It recognizes complete directive/operator names, matching header delimiters, comments between tokens, and LF/CRLF continuations, while preserving candidates in comments and inactive branches. It does not evaluate arbitrary macros; the existing material-pipeline path definition remains explicitly recognized. The shader Gem registers the staged `Builders/ShaderHeaders` directory as a scan folder so platform headers can participate in source dependencies, including installed-engine builds. Dependency events in the compiler are an observability interface; they do not replace asset dependencies discovered before compilation. `ProcessJobResponse` is not assumed to support new source dependencies.

No prepended AZSL or `.azslin` product is generated. Product sub-ID 2 stays reserved; HLSL/reflection and shader/variant identifiers remain stable. HLSL/reflection caching, platform compiler intermediates, material-generated source and AZSLC-emitted shader-option macros remain part of the pipeline. Shader and shader-variant builder version increments invalidate previous products.

## Prior art and revisions

- [Slang frontend overview](https://shader-slang.org/slang/design/overview.html#preprocessing): separate preprocessing, replacement sequences and a buffered token stream. The corresponding [preprocessor implementation](https://github.com/shader-slang/slang/blob/961e4e59ee0181ad645825c5db3a677d5a829a9f/source/slang/slang-preprocessor.cpp) was reviewed at revision `961e4e59ee0181ad645825c5db3a677d5a829a9f`, particularly pretokenized input streams, their ownership and dependency callbacks.
- [Clang token design](https://clang.llvm.org/docs/InternalsManual.html#the-token-class): source-backed spellings and preprocessing flags.
- [Clang source locations](https://clang.llvm.org/docs/InternalsManual.html#the-sourcelocation-and-sourcemanager-classes): spelling/use locations, include context and presumed locations.
- [Clang TokenLexer.cpp](https://github.com/llvm/llvm-project/blob/012428c5e864d5e976638eb9e19ea207cd2cb829/clang/lib/Lex/TokenLexer.cpp): argument handling, pasting and rescanning, reviewed at revision `012428c5e864d5e976638eb9e19ea207cd2cb829`. These algorithms informed the design; no implementation text was imported.
- [glslang Scan.cpp](https://github.com/KhronosGroup/glslang/blob/efa016659ffc4f2ae566b6b1db71a70655ac33a1/glslang/MachineIndependent/Scan.cpp): translating preprocessing tokens to parser tokens, reviewed at revision `efa016659ffc4f2ae566b6b1db71a70655ac33a1`. No implementation text was imported.
- [ANTLR C++ TokenSource](https://github.com/antlr/antlr4/blob/8e6fd9147b3c9d36b60e2b6656871a55227efb1b/runtime/Cpp/runtime/src/TokenSource.h): the adapter implements the repository-pinned 4.13.2 runtime at revision `8e6fd9147b3c9d36b60e2b6656871a55227efb1b`. The matching `ANTLRInputStream` owns decoded UTF-32; this experiment uses it only for individual token spellings.
- [Microsoft command-line parsing](https://learn.microsoft.com/en-us/cpp/c-language/parsing-c-command-line-arguments): argument-array serialization on Windows.
- [GCC include syntax](https://gcc.gnu.org/onlinedocs/gcc-9.4.0/cpp/Include-Syntax.html): header-name lexical context and literal backslash handling.

The preprocessing implementation is original code. The C++20 work additionally reviewed Clang's `Lexer.cpp`, `TokenLexer.cpp`, `PPExpressions.cpp`, `PPDirectives.cpp`, `PPMacroExpansion.cpp`, `Pragma.cpp` and Unicode tables at release [`llvmorg-20.1.8`](https://github.com/llvm/llvm-project/tree/87f0227cb60147a26a1eeb4fb06e3b505e9c7261/clang/lib/Lex), commit `87f0227cb60147a26a1eeb4fb06e3b505e9c7261`. These implementations informed lexical boundaries, prescan/pragma timing, VA_OPT placemarkers and diagnostics. No Clang implementation code is linked or imported into production sources. The Unicode ranges are the numeric ranges specified by [C++20 N4861](https://isocpp.org/files/papers/N4861.pdf), [lex.name] tables 2 and 3.

The [pinned upstream test inputs](../Tests/Preprocessor/Clang/README.md) retain their original files, SHA-256 hashes and LLVM license. Their RUN/CHECK comments are provenance, not commands executed by the harness. Future imports must record the upstream revision and preserve the relevant license.

## Shared-storage baseline (`no-mcpp-1`)

The following results were recorded before this string-copy experiment. They describe `no-mcpp-1`, not validation or performance claims for `no-mcpp-2`.

Before frontend integration, the current source-built compiler passed 380 of 383 legacy checks, with the same three existing TODOs and zero failures as the staged compiler. The source build used `build/mac_ninja_no_unity`, profile configuration. The suite took 8.94 seconds wall time; maximum child RSS reported by macOS `getrusage` was 42,385,408 bytes. This is a suite/process baseline, not a per-shader allocation measurement.

`ShaderCompiler.Tests` exercises native semantics, direct token integration and source/arena lifetime. The local results below cover the complete compiler suite, `AtomShader.Tests` and clean AutomatedTesting asset processing. Windows/Linux and editor acceptance remain separate; an unavailable runner is not a passing validation.

The native compiler subsequently passed the same 380 checks / 3 existing TODOs / 0 failures. Five real engine shaders (BRDFTextureCS, SkyBox, Silhouette, Unlit and Shadowmap) were compared using the global/macOS AZSLC options, the Metal forced header, descriptor definitions and the AutomatedTesting scan-folder include paths. IA, OM, SRG, option and binding-dependency JSON matched after accounting for the top-level `source` field changing from the temporary preprocessed file to the original AZSL path. Per-invocation measurements on this machine ranged from 0.051–0.349 seconds native versus 0.058–0.361 seconds for the previous compiler plus preprocessing; these small samples are compatibility checks, not a statistically controlled performance claim.

The standalone `ShaderCompiler.PreprocessingBenchmark` reports source, generated spelling, token and location storage plus ordinary C++ allocation counts and preprocessing/adapter time. A valid test shader containing 1,000 uses of a macro with 100 long identifiers retained 9,063 source bytes and 70 generated spelling bytes. The previous preprocessing path produced 3,000,157 flattened bytes, followed by the old compiler's UTF-32 decoding. Native preprocessing produced 201,020 ANTLR tokens, approximately 4.82 MB of preprocessing descriptors, 5.24 MB of location capacity and 27.34 MB of ANTLR wrappers. The benchmark counted 22,373 preprocessing allocations and 240,179 frontend allocations; aligned allocations, non-C++ allocators and parser/semantic allocations are outside that counter.

Compiling that valid shader with `--syntax` measured 174,112,768 bytes peak compiler RSS natively versus 231,735,296 bytes for the source-built previous compiler (about 25% lower for this workload). Wall times were 3.27 seconds native and 3.59 seconds previous compiler plus 0.052 seconds previous preprocessing. Measurements were taken during other build activity and are illustrative, not controlled throughput statistics. Compiler RSS excludes the previous preprocessing process. Token metadata remains substantial even when spelling copies are eliminated.

The final native compiler tests cover 13 CLI/integration groups, including header-name lexical context and generated spellings that cross arena blocks while surviving through reflection and emission. The C++ suite includes source/container/arena growth, repeated file identity, macro-table growth and 1,000 deterministic malformed-input cases. A standalone AddressSanitizer + UndefinedBehaviorSanitizer build of the new source/preprocessor/adapter code and its tests passed; the linked ANTLR runtime and the rest of the engine were not sanitizer-instrumented in that run.

Local profile-build validation on macOS/arm64 passed all four registered compiler/AtomShader CTest suites, including 17 AtomShader tests. A separate empty build directory configured and source-built AZSLC and its tests without resolving or staging the removed preprocessing package; its three compiler CTest suites passed. Process argument forwarding passed all eight framework tests locally. Windows command-line serialization still requires its corresponding runner.

The final clean AutomatedTesting build, using the final binaries and an empty cache in an isolated project clone, processed 5,411 assets with zero failed jobs in 454.5 seconds. All 5,405 distinct job identities matched the earlier clean pass (which reported 5,418 processing completions because jobs can run more than once); none were dropped. Its 358 shader jobs completed with zero shader errors and 35 warnings. Material-generated sources, root variants, supervariants and listed-variant jobs were present, including 81 variant-batch jobs and 25 variant-tree jobs. The final database contained no duplicate product keys or obsolete preprocessing products, and no `.azslin` files remained in the cache. Successful non-shader test assets produced 132 error diagnostics, including deliberate negative Lua/ScriptCanvas fixtures; zero failed jobs does not mean an empty error log.

Local asset dependency checks exercised normal, reverse-order and simultaneous additions, nested-header edits, deletion/recreation and cleanup. Reprocessing removed seeded legacy subtype-2 preprocessing products and their files. These checks exposed an existing uninitialized optional job-status value in the asset database's product query, causing duplicate product insertion in optimized builds. Initializing that value fixed the issue; all 96 existing database tests passed, and repeated shader rebuilds retained the expected 15 products. Compiler profiling now writes into the job temporary directory instead of beside original sources. Editing the isolated project scene SRG rebuilt dependent shaders with the added field and the correct project `#line` path; restoring the SRG rebuilt them again and removed that field.

Remaining platform acceptance must run Windows DX12/Vulkan, Linux Vulkan, the existing Windows editor dependency-chain test (`Atom/TestSuite_Periodic_Null_Render_01.py`) and live editor shader reload. These checks were not executed on the macOS host. The local batch dependency tests validate rebuilding and product cleanup, not runtime reload notifications.

A second workload exercised an include graph of 1,101 distinct files, with repeated guarded includes: 360,670 retained source bytes, 70 generated spelling bytes, exactly 1,101 file reads and 109,001 ANTLR tokens. The previous flattened output occupied 673,578 bytes before UTF-32 decoding. Native compiler peak RSS was 75,300,864 bytes versus 83,427,328 bytes previously (about 10% lower for this workload); measured times were 0.316 seconds native versus 0.243 seconds previous compiler plus 0.283 seconds previous preprocessing. Native descriptor storage was 2.62 MB, location capacity 2.62 MB and ANTLR wrapper storage 14.82 MB. These runs also overlapped asset processing, so timings are illustrative.

## String-copy experiment (`no-mcpp-2`)

These measurements and asset results precede the subsequent C++20 conformance work.

The experiment keeps native preprocessing, direct ANTLR token delivery and source provenance while replacing shared spellings with independently owned strings. Its source changes remove approximately 290 lines of implementation, including the generated-spelling arena, stable-address string storage, borrowed UTF-8 character stream and view-specific emission APIs. `SourceToken` remains a small provenance extension of `CommonToken`; it no longer supplies text storage or a custom `getText()` implementation.

The rebuilt compiler passed all four registered compiler/AtomShader suites. The legacy result remains 380 passed, three existing TODOs and zero failures. Ownership tests now verify independent token/source copies, source-location IDs across vector growth, and token text surviving destruction of its original compilation unit. The native preprocessor/adapter tests, including 1,000 bounded malformed inputs, passed with AddressSanitizer and UndefinedBehaviorSanitizer. As in the baseline, the linked ANTLR runtime and the rest of the engine were not sanitizer-instrumented.

BRDFTextureCS, SkyBox, Silhouette, Unlit and Shadowmap produced byte-identical HLSL and all five reflection JSON products compared with the saved `no-mcpp-1` binary, using the actual global/macOS flags, descriptor definitions, Metal forced header and AutomatedTesting include directories.

The string-copy compiler also passed a clean macOS/Metal AutomatedTesting asset build in an isolated project clone with an empty cache: 5,413 processing completions, all 5,405 distinct baseline job identities present, and zero failed jobs. Its 358 shader jobs had zero errors and the same 35 warnings as the shared-storage baseline. All 81 variant-batch and 25 variant-tree jobs completed. The 4,542 generated HLSL/reflection products matched the baseline after normalizing only the two temporary project directory prefixes. No duplicate product keys, reserved preprocessing products, `.azslin` files or `.azslprepend` files were present. The successful non-shader test assets again recorded 132 error diagnostics, including intentional negative fixtures. Windows/Linux and live editor acceptance were not rerun for this experiment.

The following macOS/arm64 profile-build measurements used five runs per compiler/workload, alternating compiler order. Values are medians of full `--syntax` invocation time and per-process peak RSS; they do not measure semantic analysis or emission. Both executables used the same runtime libraries. These are synthetic local comparisons, not a general performance guarantee.

|---|---:|---:|---:|---:|
| 1,000 expansions of a 100-identifier macro | 2.543 s | 2.589 s | 172.9 MB | 180.8 MB |
| 1,101-file include graph | 0.162 s | 0.185 s | 78.8 MB | 77.5 MB |

In the macro workload, the standalone benchmark counted 22,373 preprocessing allocations and 240,179 allocations through ANTLR buffering with shared storage, versus 1,023,795 and 2,647,769 with copies. In the include graph, corresponding counts were 195,949 / 327,692 versus 197,145 / 983,958. Both implementations read the same number of files and produced the same token counts. These counters cover ordinary C++ allocations only; aligned allocations, non-C++ allocators and parser/semantic allocations are excluded. The copy benchmark reports logical token spelling bytes separately from descriptor bytes; those totals are not independent heap measurements because short strings can use inline storage.

## C++20 conformance validation

`ShaderCompiler.PreprocessingConformance` is registered in CTest. Its fixed token expectations test lexical boundaries directly through the test executable; no test-side AZSL lexer is used. It covers prefixed/raw/user-defined literal tokens, Unicode macro identity, digraphs, numeric/character expressions, short-circuit diagnostics, skipped conditionals, macro rescanning, VA_OPT and pragma timing, header queries, source remapping and export round trips. It also runs 500 deterministic expression cases, 300 structured macro cases, and 36 pinned Clang inputs (29 valid and seven requiring diagnostics).

For an additional reference comparison, run:

```sh
python3 Code/Tools/ShaderCompiler/Tests/preprocessing_conformance.py \
    build/mac_ninja_no_unity/bin/profile/ShaderCompiler.Tests \
    build/mac_ninja_no_unity/bin/profile/azslc \
    --reference /path/to/clang
```

The reference compiler runs with `-E -P -x c++ -std=c++20 -pedantic-errors`. Its output is lexed in preprocessed mode to compare token spellings; separate fixed-token cases test lexing independently. Neither the reference compiler nor network access is required for normal CTest runs. Expected output must not be revised just to accommodate a native failure. Differences in implementation-defined character choices, unsupported AZSL language features or later-standard extensions must be reviewed against the selected baseline.

The conformance suite is a regression gate, not a proof covering every possible input or every future language version. Shader/asset compatibility, preprocessing semantics, diagnostics and malformed-input robustness are separate validation requirements. New discrepancies require minimized regression cases before a fix is accepted.

The final C++20 source build on macOS/arm64 passed all five compiler/AtomShader CTest suites: 380 legacy checks passed with the same three existing TODOs and zero failures, all 18 conformance groups passed, and all 21 AtomShader tests passed. The optional Clang 23.1.0 comparison passed the same conformance groups, including the 36 pinned inputs. The native source/preprocessor/adapter tests and conformance cases also passed AddressSanitizer and UndefinedBehaviorSanitizer; the linked ANTLR runtime, emitter and engine were not sanitizer-instrumented.

Asset validation exposed quadratic behavior in the existing dependency regex after adding header queries. Dependency discovery now uses an independent forward-only scanner with no regex dependency. Its regression tests include a roughly 500 KB file, complete identifier boundaries, comments, continuations, inactive branches, and every truncated prefix of an include directive. The large-file test took 4 ms in the local profile build. The native preprocessor already used byte/token scanning and was unaffected by this replacement.

The final clean macOS/Metal AutomatedTesting run reached all 5,405 jobs. Thirteen shader jobs initially failed in Apple's Metal toolchain launcher, and six dependent jobs failed as a consequence; native AZSL and HLSL generation succeeded for those shaders. Xcode reported the toolchain installed, and directly compiling a failed job's generated Metal source succeeded. Reprocessing the affected sources through AssetProcessor, without changing shader sources or compiler behavior, cleared all failures. The initial pass took 491.4 seconds and the reprocess pass 50.0 seconds.

The final database contains 5,405 completed jobs, including 358 shader jobs with zero errors and the baseline 35 warnings, 81 variant-batch jobs, 25 variant-tree jobs and 123 shader-variant jobs. It contains 4,542 HLSL/reflection products and no duplicate product keys, reserved preprocessing products, `.azslin` files or `.azslprepend` files. Successful non-shader negative fixtures retain the baseline 132 error diagnostics. Production configuration, linked shader-builder libraries and staging manifests contain no mcpp dependency. Windows DX12/Vulkan, Linux Vulkan and live editor acceptance remain outstanding on their corresponding runners.

A separate asset dependency check used a shader whose only reference to an optional header was `__has_include`. With the header absent its emitted constant was 17; adding the header automatically rebuilt the shader with 29, and deleting it rebuilt the shader with 17 again. Neither the shader source nor its descriptor was changed or explicitly forced during those transitions. The temporary test shader was removed afterward.

After consolidating compiler argument APIs, all five compiler/AtomShader suites and eight process-launch tests passed again. Asset reprocessing caught two SPIRV-Cross failures caused by the inherited MSL version; explicitly removing the inherited switch/value pair fixed the macOS configuration. The subsequent macOS/Metal pass reran all 358 shader jobs, 81 variant batches and 25 variant trees successfully in 157.9 seconds. The 5,405 job identities, shader warning count and HLSL/reflection product count remained unchanged, with no failed jobs or obsolete preprocessing products. The Metal and Vulkan builder sources compiled locally; Windows DX12 and iOS execution still require their platform runners.
